# 值得追的 agent 應用與開發來源

整理日期：2026-09-08
目的：日常生活／穿戴／工作場景的 agent 應用分享，以及 agent 開發新知。

## 怎麼判斷值得看

第一輪搜尋回來的全是農場文（「2026 年十大 AI agent 完整指南」那種），
特徵：作者是廠商行銷、沒有第一人稱、沒有數字、沒有 repo、標題有年份和數字。**直接跳過。**

值得看的三個訊號（這也是業界公認的判準）：
1. **秀出過程**——程式碼、prompt、截圖、失敗紀錄
2. **對不確定性有校準**——講清楚什麼是量過的、什麼是猜的
3. **錯了會自己更正**

## 第一級 · 確定值得長期追

### Simon Willison — <https://simonwillison.net>
**為什麼可信**：Django 共同作者、Datasette 與 `llm` CLI 的作者。
每天寫，常常一天好幾篇，全部第一人稱、全部來自親手用過。
也是 prompt injection（提示注入攻擊）這個題目最權威的人。

**怎麼讀**：他有分類 tag stream，直接訂你要的那條——
`agentic-engineering`、`coding-agents`、`ai-assisted-programming`。

**2026 的主線**：他在做一個 **Agentic Engineering Patterns** 專案，
收集「用 coding agent 寫軟體」的實作模式。主文 2026-02-23：
<https://simonwillison.net/2026/Feb/23/agentic-engineering-patterns/>
（他自己說那份東西大部分程式是 Claude Opus 4.6 在 Claude Code for web 裡寫的。）

**適合你的部分**：agent 開發新知、安全性。他不太寫穿戴。

### Hamel Husain — <https://hamel.dev>
**為什麼可信**：幫 50 家以上公司建過評測系統，教過 4,500 位以上學生，
學生來自 500 多家公司（含 OpenAI、Anthropic、Google）。
他不賣框架，他賣「怎麼知道你的東西有沒有在運作」。

**必讀兩篇**：
- AI Evals：Everything You Need to Know（FAQ 形式）
  <https://hamel.dev/blog/posts/evals-faq/>
- A Field Guide to Rapidly Improving AI Products（錯誤分析與改進流程）

**2026-03-02 新的**：Evals Skills for Coding Agents（與 Shreya Shankar 合著）
<https://hamel.dev/blog/posts/evals-skills/>
主題是「教 coding agent 自己跑產品評測」。

**適合你的部分**：這是 [05-導讀](05-導讀.md) 那篇作者引用的人。
你們 SDK 每輪都在做稽查與測試，這條線直接對得上。

### Dex Horthy（HumanLayer 執行長）
**為什麼可信**：**「context engineering」這個詞是他造的。**
2025-04 寫了 **12-Factor Agents — Principles for building reliable LLM applications**，
是實務界被引用最多的那份 agent 原則文件。寫之前他訪談了大約 100 位真正在做的 AI 工程師。

主張：把 agent 當成模組化、**以確定性為主**的軟體來建。
關注點：JSON 解析、控制 prompt 與 context window、掌握控制流、把人接進迴圈。

**入口**：<https://ai.engineer/speakers/dex-horthy>
比較深入的訪談（Pragmatic Engineer）：
<https://newsletter.pragmaticengineer.com/p/context-engineering-with-dex-horthy>

**適合你的部分**：他的結論跟 [01-導讀](01-導讀.md)、[02-導讀](02-導讀.md)
是同一件事的更早、更系統化的版本。**如果只讀一份 agent 設計原則，讀這份。**

### Anthropic Engineering — <https://www.anthropic.com/engineering>
**為什麼可信**：第一手。做模型的人自己寫怎麼用。

**三篇基礎**：
- Effective context engineering for AI agents（2025-09-29）
- Equipping agents for the real world with Agent Skills（2025-10-16）
- Building agents with the Claude Agent SDK（2025-09-29）

其中 context engineering 那篇的核心論點值得記：
**每個前沿模型在 context 變長時都會可量測地變差，而且遠在視窗真的填滿之前就開始。**
所以要決定「哪些 token 有資格佔用這一步的 context」。

**適合你的部分**：Agent Skills 那篇跟 [02-導讀](02-導讀.md) 的 skill 設計直接對照。

### swyx / Latent Space — <https://latent.space>
**為什麼可信**：辦 AI Engineer World's Fair（2026 年 6,000 位以上工程師）。
他的角色是**產業的目錄**——哪些工具、模式、研究方向真的有人在採用。
電子報 + podcast，題目涵蓋 eval、推論經濟、agent 框架、模型與產品之間那層工具。

**適合你的部分**：一週看一次抓風向。不適合拿來當技術細節來源。

### Kwindla Hultman Kramer（Daily 執行長，Pipecat）
你已經讀過他那篇（[05-導讀](05-導讀.md)）。
**為什麼可信**：從 GPT-4 剛出就在做語音 agent，幫很多團隊從 PoC 走到規模化生產。
Pipecat 是被廣泛使用的開源語音 agent 框架。

**適合你的部分**：**走眼鏡／語音路線的話，他是這個領域最實務的人。**
Pipecat Flows（對話狀態機）是可以直接用的東西。

### Geoffrey Litt — <https://www.geoffreylitt.com>
**為什麼可信**：Ink & Switch 資深研究員（現在在 Notion）。
2025 年與 Josh Horowitz、Peter van Hardenberg、Todd Matthews 合寫
**Malleable Software: Restoring User Agency in a World of Locked-Down Apps**
<https://www.inkandswitch.com/essay/malleable-software/>

核心主張：軟體應該讓使用者能低摩擦地重塑成自己要的樣子；
修改變成日常、適配發生在使用的當下，而不是透過遙遠的工程團隊。
他們也直說：**AI 很重要，但單靠 AI 不足以帶來個人軟體的新時代。**

**適合你的部分**：這是「agent 住進我原本的工具裡」這件事的**思想框架**。
[03-導讀](03-導讀.md) 那篇是同一個想法的實務版。寫 pitch 要引用概念時很好用。

## 穿戴式裝置：誠實說，實務文章很少

這是目前最缺第一手經驗分享的領域。**沒有人在寫「我做了一個眼鏡 agent，這是我學到的」。**
現有的是廠商公告和企業案例。以下是真的有內容的：

### Meta 開放 Ray-Ban Display 給第三方開發者（2026-05）
<https://developers.meta.com/blog/build-for-display-glasses/>

**這是目前最重要的一則**——第一次有第三方開發者可以對一台
**已經在市面上販售**的消費級 AI 眼鏡的內建顯示器寫東西。

兩條開發路線：
1. **原生**：Meta Wearables Device Access Toolkit（iOS 用 Swift、Android 用 Kotlin）
2. **Web Apps**：直接用 HTML／CSS／JavaScript 寫，跑在眼鏡上

輸入方式：**Meta Neural Band** 的手勢控制，用 sEMG（表面肌電）偵測細微的手指與手部動作，
不靠觸控、不靠語音。原文的說法是「更隱蔽、更即時的控制，
使用者不必說話也不必去摸眼鏡」。

**對你的用處**：Web Apps 那條路線 = HTML/CSS/JS 就能寫眼鏡介面。
這對 4 小時的黑克松是很重要的資訊。

### NVIDIA XR AI（公開 beta）
<https://blogs.nvidia.com/blog/nvidia-xr-ai/>
給開發者的框架，用來為 AR 眼鏡與 XR 裝置建**多模態 AI agent**。

案例：Siemens 在研究讓工廠工程師戴輕量眼鏡，
問 agent 維修資訊、排除故障、驗證作業、記錄現場發生了什麼。
（他們用 NVIDIA DGX Spark——跟你們的 spark 平台是同一類硬體。）

### 一個關鍵的架構觀點（來自 Snapdragon START，2026-06）
一個 AI 不綁定的堆疊，連接穿戴裝置、手機伴侶 app 和雲端服務。
背後那個工程現實值得記住：

> **眼鏡可能發起任務，但真正執行動作的往往是手機、雲端、服務帳號或企業後端。**

**這句對你的黑克松設計很有用**：不要想把 agent 塞進眼鏡裡。
眼鏡負責看、聽、顯示；動腦和動手的在別的地方。

### 企業應用的形狀
現場工作的檢查與合規：把拍下來的紀錄自動變成結構化報告。
例子：Airwave —— ANSI 認證的安全眼鏡，把錄下的現地作業
直接變成檢查報告、危害分析、以及隨問隨答的訓練解答。

## 工作場景

### Slack 官方：Agent-First Workspace
<https://slack.com/blog/news/agent-first-workspace-slack>
**注意這是廠商行銷，但裡面兩個數字和一個問題陳述有價值：**

- 自一月以來，在 Slack 上建的自訂 agent **成長超過 300%**
- 他們點出的問題叫 **agent sprawl（agent 蔓延）**：
  各團隊各自在不同平台部署 agent，這些「數位同事」在各自的孤島裡工作，
  **沒有共享脈絡，agent 就只是另一個雜訊來源。**

**對你的黑克松很好用**：這正好是「住進人們已經在的地方」為什麼重要的商業論證。
如果走 Slack 路線，pitch 可以直接打這個痛點。

### MLflow：Building Production-Ready AI Agents in 2026
<https://mlflow.org/articles/building-production-ready-ai-agents-in-2026/>
結論跟你已經讀的那幾篇完全一致：

> 生產環境的可靠性來自**模組化設計、嚴謹的狀態管理、確定性的護欄**，
> 不是來自更好的 prompt。

還有一句值得記：在 notebook 裡讓 agent 動起來，
跟讓它在規模下可靠運作，是**根本不同的兩件事**——
後者需要的是分散式系統工程、執行期治理、嚴謹的評測。

### 組織層面最常犯的錯（多篇共同觀點）
不是技術問題，是組織問題：沒有量測計畫、把所有形狀的 AI 工具當成同一種東西、
跳過護欄、以及繞過資深工程師的自上而下推行。

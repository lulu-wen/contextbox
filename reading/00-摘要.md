## 01 · How to Build Antifragile Agents with OpenRouter
Kenny Rogers（OpenRouter DevRel Lead）· 16 分鐘 · 2026-08-05
[中文導讀](01-導讀.md)　·　[英文原文](01-openrouter-antifragile-agents.md)　·　<https://post-training.aitinkerers.org/p/how-to-build-antifragile-agents-with-openrouter>

背景：2026-06-12 Anthropic 為配合美國政府指令對所有客戶停供 Fable 5，
07-01 才恢復，中間 19 天空窗。所有押單一模型的應用都被打到。

作者做了一個訂閱扣款客服 agent（判斷退款／折抵／駁回／轉人工），示範怎麼讓它「反脆弱」
（antifragile：不只是不怕壞，是壞掉之後還能順勢變更好）。

**這篇最值錢的一段是 Step 4「把模型的工作縮小」**，數字很暴力：

| 架構 | 20 題全對 | holdout | 成本 | 中位延遲 |
|---|---|---|---|---|
| Fable 5，全交給模型判斷 | 14/20 | 6/8 | $0.6719 | 11.03 s |
| Grok 4.5，全交給模型判斷 | 5/20 | 2/8 | $0.0840 | 3.91 s |
| Fable 5，**拆解後** | 20/20 | 8/8 | $0.1492 | 5.81 s |
| Grok 4.5，**拆解後** | 20/20 | 8/8 | $0.0555 | 3.54 s |

拆解方式：模型只負責讀客戶的自然語言，吐出 3 個欄位的結構化意圖
（workspace、reason、scope）；算錢、選政策版本、查爭議、擋重複退款
全部交給有單元測試的 TypeScript。

> 原則（值得抄在牆上）：模型適合讀凌亂的語言、比對模糊的指涉、把請求變成結構；
> 程式適合算數、門檻、權限、idempotency、政策分支。

其他重點：
- OpenRouter 的 **preset** 把「主模型 + fallback 順序」存在應用外面，
  換模型順序不用改程式、不用重新部署。`models` 陣列會照順序試。
- 別做「只看結論」的 eval。要把 6 個欄位分開評分——「同意退款」但退錯發票也是錯的。
- 12 題開發用 + 8 題凍結 holdout，測「換句話問還會不會對」。
- 追蹤誰回答了：Router metadata 查單筆、Broadcast 匯出到 ClickHouse／Langfuse 等看趨勢。

**對這場黑克松的用處**：OpenRouter 是贊助商，這是官方口徑的用法。
更重要的是那個拆解原則——4 小時內做出可靠 demo 的最佳策略就是**把模型的工作縮到最小**，
其餘寫死在程式裡。現場網路不穩時，preset fallback 也能救命。
可跑的範例 repo：<https://github.com/kenrogers/antifragile-refund-triage>

## 02 · How to Write a Winning Agent Harness for Your Domain
Hitesh Jain（Coral Bricks AI 創辦人，前 Meta AI Principal Engineer）· 13 分鐘 · 2026-06-24
[中文導讀](02-導讀.md)　·　[英文原文](02-agent-harness-for-your-domain.md)　·　<https://post-training.aitinkerers.org/p/how-to-write-a-winning-agent-harness-for-your-domain>

開場一句話就是重點：**加指令讓 agent 變差，通常不是 prompt 問題，是 harness 問題。**
（harness 是「馬具」，這裡指包在模型外面那層組織邏輯的框架。）

他們的金融 agent 曾長到 2,500 行指令 + 50 幾個工具定義，很多互相重疊衝突，
再加指令沒用了。於是做了 **Reef**——skills-first、git-native 的極簡 Python harness。
<https://github.com/Coral-Bricks-AI/coral-ai>

三個基本元件：
1. **Skill** = 一個 markdown（程序性指令）+ 選配的 `impl.py`（`@skill_fn` 裝飾的函式）。
   一個裝飾器同時綁住 prompt 指令、JSON Schema、Python 函式。
2. **Agent type** = 人格 prompt + 一份 skill 索引。
3. **Runtime constraint** = 用程式強制，不靠 prompt 拜託。

控制變數的實驗結果（同模型 Kimi K2.6、同資料、同評審，n=239）：

| 設定 | 通過率 |
|---|---|
| A 參考 harness | 44.87% |
| B 只換更好的檢索 | 49.8% |
| C 完整 harness（69 skills + 專用工具） | **82.6%** |

換好的檢索只值 5 分，**剩下 33 分全來自 harness 結構**。
其中約 55% 來自「把領域慣例寫成有型別的函式」，約 28% 來自 planner 編排。

四個踩過的坑（按代價排序）：
- **skill 裡放 N-shot 範例** → 模型過擬合到範例，遇到長得不像的輸入就漏。
  寧可一條清脆的硬規則、零範例。
- **讓模型不呼叫工具就直接給答案** → 設 `min_tool_calls_before_final`，
  runtime 偵測到就注入一段強制訊息把 loop 續下去。
- **在 prompt 裡拜託「不要用 X 之後的資料」** → 它不會可靠遵守。
  用裝飾器 `@time_bounded(mode="inject")` 直接覆寫掉模型給的日期。
- **把全部工具 schema 塞進 system prompt** → 又貴又害路由變糟。
  改成先給索引，用 `load_skill()` 按需載入。

**對這場黑克松的用處**：這篇直接對應到你們 ameba-sdk 的 tool search 那條待做項目——
「先給索引、按需載入」就是那件事的做法。另外「拿掉工具 schema、最後一步強制產出 JSON」
這招在 demo 場合特別實用：保證 agent 一定會收尾，不會在評審面前無限跑。

## 03 · What I Learned Deploying OpenClaw Beyond Demos
Kaya Jones（Forever 22 創辦人）· 11 分鐘 · 2026-03-15
[中文導讀](03-導讀.md)　·　[英文原文](03-openclaw-beyond-demos.md)　·　<https://post-training.aitinkerers.org/p/what-i-learned-deploying-openclaw-beyond-demos>

**這篇最貼題**——整篇就在講「agent 在什麼地方才會變成真的有人用」。
她做客戶案子三個月的結論：留得下來的 workflow 都是同一個形狀。

> 1. 它住在人們原本就在用的工具裡。
> 2. 它把脈絡帶著走，不是每次從零開始。
> 3. 它省時間，又不需要你一直盯著。

客戶案子裡真的留下來的（可以當題目靈感清單）：
每日簡報、個人 CRM（存在 Obsidian）、家庭排程 bot（活在 iMessage 群組裡）、
餐廳電話訂位（Resy／OpenTable 資料不全時直接打電話）、開會前的人物／公司 dossier、
人脈關係圖（誰認識誰，找暖介紹）。

> 共通點：OpenClaw 從「玩具聊天介面」變成「背景基礎設施」時才開始有價值。

研究 agent 那節有個反直覺的設計，很好用：**讓「沉默」是可接受的輸出。**
她的指令寫「如果好論文少於 3 篇，回 NO_REPLY」。
三條規則：先從一個結構化、可預期的來源開始；讓沉默可接受；先調好過濾再加資料源。

還有 SnapshotClaw——把 agent 的 config、cron、skills、memory 做版本控制。
理由不是備份本身，是「知道能回到已知良好狀態」之後她才敢亂搞。

機器人那節（Hugging Face Reachy Mini + OpenClaw brain，在 AI Tinkerers NYC demo）
語音管線：`Mic → VAD → STT（Nemotron／Whisper）→ Claude via OpenClaw → ElevenLabs TTS → Speaker`
她的結論值得抄：**魔力不在「有身體」，而在那個實體介面接進了一個已經懂你脈絡的持久數位系統。**
Demo 隔天她接上 Spotify 控制，機器人才從「展示品」變成「真的在用的東西」。

**對這場黑克松的用處**：這篇幾乎就是評審心裡的評分表。
如果走眼鏡那條路，那句「實體介面 + 已經懂你脈絡的持久系統」就是 pitch 的骨幹——
不要只 demo「眼鏡會講話」，要 demo「眼鏡接上了我原本的工作流」。

## 05 · Your Conversation Is Out Of Distribution
Kwindla Hultman Kramer（Daily CEO，Pipecat 貢獻者）· 8 分鐘 · 2025-09-11
[中文導讀](05-導讀.md)　·　[英文原文](05-voice-out-of-distribution.md)　·　<https://post-training.aitinkerers.org/p/your-conversation-is-out-of-distribution>

語音 agent 為什麼特別難：對話都很多輪，而且**人說話跟人寫字不一樣**。
模型訓練資料裡多輪對話只佔一小部分，對話語音更少，所以語音 agent 一直踩在
「鋸齒狀邊界」（jagged frontier，指模型能力忽強忽弱那條不規則的界線）上。
連最好的模型在多輪對話都會明顯退化。參考論文：LLMs Get Lost In Multi-Turn Conversation。

解法叫 **context engineering**（脈絡工程，Dex Horthy 命名）：
既然你餵的 token 有點「不在訓練分布內」，那就餵它更好的 token。
他的做法是把複雜語音流程設計成簡單有彈性的**狀態機**，每一步只給模型：

1. 專注在這一件事的 system prompt
2. 到目前為止對話的「切題摘要」（順手清掉多輪對話的雜訊）
3. **只有這一步用得到的工具**（工具選項越少，tool use 表現明顯越好）
4. 可以轉去哪些下一個狀態的說明

開源工具：Pipecat Flows（建在 Pipecat 上的即時對話狀態機）。

他自己寫的 30 輪語音對話 benchmark 結果：**沒有一個模型接近完美**，全都有錯。
（那個測試刻意不做任何 context engineering，就是要看裸測有多慘。）

對 eval 的態度也務實，順序很重要：
先自己天天用 → 再手動大量認真測 → 再做很簡單的 eval 輔助手測 →
再做可重複跑的 eval → 最後才是模擬式大規模測試。
跳過前三步直接做花俏的 eval 沒用，因為你根本不知道自己的 eval 有沒有意義。

**對這場黑克松的用處**：如果走語音或眼鏡路線，這篇是保命符。
只有 4 小時 + 現場很吵 + 評審會亂問——**別做開放式多輪對話**。
做成狀態機，每一步只給少數工具。這是「demo 不會爆」和「demo 會爆」的差別。

## 06 · What I Learned Giving Fable 5 a Face
Ben Carr（Anam.ai 技術共同創辦人）· 11 分鐘 · 2026-07-30
[中文導讀](06-導讀.md)　·　[英文原文](06-giving-fable-5-a-face.md)　·　<https://post-training.aitinkerers.org/p/what-i-learned-giving-fable-5-a-face>

第一句就是重點：**給 agent 一張臉，最難的部分幾乎跟臉無關。**
模型接進去花一小時，剩下全是外圈那層：輪替、插話、延遲、嘴型同步。

> 感覺像不像真人，主要是**時間問題**，不是畫質問題。
> 一張照片級真實的臉如果慢半拍，讀起來就是壞掉；
> 一張普通的臉如果反應像人，讀起來就是活的。

人類自然輪替的空檔只有幾百毫秒。Anam 的 agent 回應平均 180ms、首幀約 100ms。
超過半秒，人就開始把延遲解讀成猶豫，然後開始搶話填補空白。

只有上線才會遇到的失效模式：
- **插話**：停音訊不夠，臉還有在途的影格，要看得出來停止說話並開始聽；
  而且對話歷史要記「實際說出口的」而不是「排隊要說的」。
- **輪替不通用**：土耳其語必須關掉積極的 end-of-turn 偵測，因為模型一直切斷說話者。
  英語裡「我講完了」的語調線索不會轉移。做多語言要預留這個成本。
- **思考時間是看得見的**：聊天視窗裡 3 秒是個你學會忽略的轉圈圈；
  一張臉看著你的時候，3 秒很久，而凍住的臉幾乎立刻變詭異。
  臉在模型思考時必須**還在做某件事**：待機微動、傾聽表情。
- **嘴型必須生成，不能後配**：先用 diffusion transformer 把音訊轉成動作嵌入
  （頭部位置、視線、唇形、表情），再用渲染模型套到參考圖上。
  表情從音訊本身推導，所以嘴和聲音不會飄開。

**什麼時候不該加臉**：如果你的 agent 本質是一張表單（訂位、查詢、交易流程），
臉只會給一件本來想當按鈕的事加上延遲和社交儀式。
> 「沒有人想跟包裹追蹤器眼神交流。」
判準：**在人類本來會開鏡頭出現的場合才用臉。**面試、銷售、家教、教練——對話本身就是產品的場合。

**對這場黑克松的用處**：這篇是「in the room」路線的紅綠燈。
如果眼鏡 agent 的本質是「幫我查東西」，那不需要臉也不需要來回對話，
做成即時、單向、低延遲的疊加顯示反而更強。
那句「延遲預算幾百毫秒」也是硬指標——demo 之前先量自己的端到端延遲。

## 07 · MathCat：香港小學適性學習平台（talk 說明）
Natalia Kojoukhova（BAT）· AI Tinkerers 香港場 · 2026-08-31 · Top AI Demos #43 本期首選
[全文與筆記](07-mathcat-hk-talk.md)　·　<https://mathcat.fun/>

四個可抄的點：
1. **他刻意講後端不講畫面**，遊戲 UI 只「briefly show」——這社群獎勵工程判斷，不是截圖。
2. **deterministic 與 probabilistic 的平衡**是他整場的第一重點。
   小學數學題的結構、難度、答案驗證全可程式化；LLM 只負責把題目講成自然的人話。
   （與 01、02 同一結論的第三次獨立出現。）
3. **AI critic（Gemini + GPT-5）打分在「題目模板」上，不是每一題上**——四個面向：
   廣東話自然度、香港學校用語、提示品質、年齡合適度。離線跑一次，即時路徑不含 LLM 評分。
4. **適性難度靠確定性邏輯**：mastery gate、近期正確率視窗、技能解鎖。不叫模型判斷。

另外兩點：用 PWA（零安裝，評審點連結就能玩，很適合「in your pocket」）；
**贏在地方性**——對齊香港 EDB 課綱與廣東話，全球沒人能複製。

## 六篇合起來的三個結論

1. **把模型的工作縮到最小。** 模型讀語言、出結構；算數和規則寫進有測試的程式。
   （01 的 14/20 → 20/20，02 的 44.87% → 82.6%，07 的「deterministic 與 probabilistic 的平衡」，
   三篇獨立來源同一個結論。）

## 一 · 一人公司，LLM 費用 $0 / 月 【HN 已驗】

<https://news.ycombinator.com/item?id=47296664>

**這是我找到最開眼界的一個。**

一個人用 4 個 agent 跑自己的公司：

- 社群內容生成：**每天 8 篇**，跨多平台
- 社群互動：自動回覆
- 研究：抓 RSS、Hacker News、網頁爬取
- 業務開發：資安掃描找潛在客戶
- 維運：監控 7 個端點

**技術棧**：Gemini 2.5 Flash（免費層）、OpenClaw、
**WSL2 上 25 個 systemd timer**、React/TypeScript/Vite、Vercel、Firebase、
Telegram Bot、Jina Reader。

**成本**：LLM **每月 $0** —— 每天只用掉免費層 1,500 次請求裡的 **105 次**。
基礎設施約 $5/月。

**成果**：27 個 Threads 帳號、1.2 萬以上追蹤、330 萬以上瀏覽、62 支腳本、19 份情報檔。

### 最有價值的是留言裡那個技術洞見

有人問他怎麼可能只用 105 次請求。關鍵是：

> **agent 從來不進行長對話。** 每次請求就是三步：
> （1）讀預先算好的情報檔（本地 markdown，**0 token**）
> （2）一個聚焦的 prompt，把所有需要的脈絡塞進去
> （3）一個回應。

**這就是 context engineering 最省的形態。** 沒有多輪、沒有累積的對話歷史。
情報是離線算好存成檔案的，用的時候只是讀檔。

跟你讀過的 [01-導讀](01-導讀.md)「把模型的工作縮到最小」是同一件事，
但推到極端：**連對話都不要**。

### 但留言也拆穿了他一部分

這是為什麼要讀留言：

- 有人問：那 1.2 萬追蹤者**有多少真的轉成收入**，還是只是躺在那裡的死重？
- 有人指出他的儀表板動畫**是預先做好的，不是即時資料**

**作者的回應很誠實**：承認儀表板的限制、承認批次回覆用的是預先草擬的答案、
並說明真正的客戶工作和真實互動**還是人在做**。收入來自客戶專案和一個 SaaS 產品。

**教訓**：這個架構是真的、省錢是真的、規模是真的。
但「agent 跑我的公司」這個說法要打折——**agent 做的是量產與監控，不是判斷與交付。**

## 二 · 一個自主 agent 跑了兩個月的公開失敗 【HN 已驗】

<https://news.ycombinator.com/item?id=49383353>

我打不開他的完整日誌，但**留言就是全部的重點了**：

- 一位留言者形容整件事有點憂鬱，比作「Marvin 那個憂鬱機器人試著做生意」
- 另一位覺得又悲又好笑，引用了 agent 自己說的一句話：
  > **「我讀不到我自己的 log。」**

**這句話值得記住。** 自主性沒有可觀測性，就是這個下場。

呼應 [03-導讀](03-導讀.md) 裡 SnapshotClaw 的那個教訓：
agent 的狀態變成有價值的東西之後，它需要一個復原計畫。
這裡多一層：**它也需要一個「看得見自己」的計畫。**

## 三 · Ask HN：有人真的在生產環境跑 agent 嗎 【HN 已驗】

<https://news.ycombinator.com/item?id=46917293>

**這個討論串的價值在於它有多空。**

我打開時預期會看到一堆人分享自己的架構。實際上：
**沒有一個留言者描述自己真實的生產部署、效能數字、或真實的失效模式。**

有的只是工具推薦（Claude Agent SDK、Open Hands）和一個把需求拆成
「內部員工用／產品功能／對客戶」三套系統的建議。

還有一個一直出現的張力：想要自架的組織要面對很高的基礎設施成本，
而前沿實驗室的模型表現又勝過開源替代品——**隱私與能力之間的取捨。**

**教訓**：「agent 很紅」和「有人真的在生產環境跑 agent」之間的落差，
比社群媒體的音量讓你以為的還要大。

這對你反而是好消息：**你們 SDK 那套稽查流程和真人 e2e 驗證，
在這個領域是稀有的，不是理所當然的。**

## 五 · 排程型 agent：具體的做法 【混合來源】

這一類最常見，而且形狀高度一致。

### 早晨簡報 【彙整文】
大家都設 **7–8 點**。agent 去查已連接的服務，綜合成一份格式化的簡報，
推到 Telegram、WhatsApp 或慣用的訊息軟體。

### 每日回顧 agent 【搜尋摘要】
**每天下午 6 點**：讀會議筆記工具（Granola）和 Slack 訊息，
綜合之後**附加到當天的日記筆記裡**。

### 收件匣管理 【彙整文】
被報告最多的用途之一。讓 agent 大量處理 email：
退訂雜訊、按急迫性分類、草擬回覆等人審、**幾天內清掉幾千封**。

### 老化 PR 巡檢 【搜尋摘要】
一個開發者做的 Claude Code 例行任務：檢查**超過 12 小時**沒動的開放 PR，
評估是否已可合併，然後決定**是自己繼續做下去、還是需要人介入**。

（注意那個「決定要不要叫人」——這就是 human-in-the-loop 做在正確的位置。）

## 七 · 從這些案例歸納的六個模式

1. **最省的架構是「不要對話」。**
   預先算好的情報檔 + 一次性 prompt + 一個回應。這是 $0/月 的來源。

2. **訊息軟體是主要介面，不是網頁。**
   Telegram、WhatsApp、iMessage、Slack。沒有人為這些 agent 做網站。
   （這正好是這次黑克松「Channels」的意思。）

3. **排程勝過隨叫隨到。**
   25 個 systemd timer、cron、每天 7 點、每天 6 點、每 12 小時。
   最有用的 agent 不等你開口。

4. **沉默是功能。**
   [03-導讀](03-導讀.md) 的 `NO_REPLY`、那個 PR 巡檢的「要不要叫人」。
   知道什麼時候不要打擾你，是產品力。

5. **自主性必須配可觀測性。**
   那句「我讀不到我自己的 log」就是反例。

6. **量產與監控可以交給 agent；判斷與交付還是人。**
   $0 那位作者自己承認的界線。**這是目前誠實的邊界。**

## 對這次黑克松最能直接用的兩件事

**A. 那個 $0 架構就是你 4 小時的最佳策略。**
不要做多輪對話 agent。做成：預先準備好的資料 → 一次性 prompt → 一個結果。
快、穩、便宜，而且現場網路爛也不怕。

**B. 訊息軟體 + 排程 是被驗證最多次的形狀。**
如果你要走保險路線，做一個「住在頻道裡、按排程主動出現、
而且知道什麼時候該閉嘴」的 agent，這個形狀有最多真實案例背書。

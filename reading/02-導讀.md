# 導讀 · How to Write a Winning Agent Harness for Your Domain

原文：[02-agent-harness-for-your-domain.md](02-agent-harness-for-your-domain.md)
作者：Hitesh Jain（Coral Bricks AI 創辦人，前 Meta AI Principal Engineer）· 13 分鐘 · 2026-06-24
開源 repo：<https://github.com/Coral-Bricks-AI/coral-ai>

> 重點導讀，不是逐句翻譯。

**先解釋一個字**：harness 原意是「馬具」。這裡指包在模型外面那一層——
組織條件邏輯、管工具、管流程的框架。不是 prompt，也不是模型本身。

---

## 開場：一句話的診斷

> 如果你的 agent 加了指令會變好，然後**突然變差**，
> 那可能不是 prompt 問題，是 harness 問題。

他們的親身經歷：本來用 Kimi K2.6 做金融研究 harness，在舊版基準
（Vals AI v1）上大幅領先，正打算在 Opus 4.8 發布那週宣布。
結果 Vals AI 發了 v2，Anthropic 拿 Opus 4.8 在 v2 上示範，
聚光燈一夜之間移到更難的基準。**他們在 v2 上的分數跟參考 harness 一模一樣，領先歸零。**

除錯時發現：v2 的問題讓模型想更久、用更多輪、然後**跑完 token 預算**。
而他們的 prompt 已經長到 **2,500 行指令 + 50 幾個工具定義**，
很多互相重疊甚至衝突。再加指令完全沒用了。

於是有了 **Reef**——輕量、領域中立、skills-first、git-native 的 harness 框架。

---

## Reef 是什麼

一個給「規則很重的領域」用的極簡 Python agent harness：

- 能力組織成**版本控制的 skill 資料夾**（`SKILL.md` 程序指令 + `impl.py` 函式）
- skill 在 system prompt 裡只放**精簡索引**，需要時才載入
- 一個可讀的 ReAct 迴圈管：模型呼叫、工具派送、重試、執行期約束
- 重視 git 可維護性、窄而可組合的 skill、低額外開銷

**ReAct** 是常見的 agent 迴圈模式：模型輪流「想一下 → 呼叫工具 → 看結果 → 再想」。

三個基本元件組成一切：**skills、agent types、runtime constraints**。

### 5 分鐘試跑

```bash
git clone https://github.com/Coral-Bricks-AI/coral-ai.git
cd coral-ai
python -m venv .venv && source .venv/bin/activate
pip install -e .
export LLM_API_KEY=sk-...

```

repo 裡有兩個參考實作：
- **Equities** —— 刻意做到最薄的 hello-world（1 個 sub-agent、2 個 skill、無 planner）
- **AlphaCumen** —— 打贏公開金融基準的那個（6 個專家 + planner、69 個 skill、
  約 40 個有 Python 綁定、約 25 個 planner skill、6 個索引語料庫、
  三種執行期約束）

從沒做過 harness 的從 Equities 開始；領域已經到「20+ skill、多實體問題」的
複雜度就從 AlphaCumen 開始，複製 planner 與專家的骨架、把 skill 內容換掉。

## Step 1 · 設計一個 skill

**skill = 可重用的領域能力單位**。一個 markdown（程序性指令）+ 選配的 Python 模組。

### skill 的 markdown 怎麼寫

> **skill 承載原則，不是大量範例。**
> 硬規則能推廣到模型沒見過的形狀；N-shot 範例會教模型去比對範例的樣子，
> 於是漏掉長得不像的輸入，而且會把測試集的用詞漏進 prompt 裡。

每個 skill 宣告它屬於哪個 agent（`applies_to:`）和什麼時候該用（`when:`）。
建置時 harness 用這些標籤組出每個 agent 的索引。

```
applies_to: [sector_analyst]
when: 跨標的、多時間窗的價格表現問題
HARD RULE 0 —— 多標的 × N 日期的價格報酬問題：
第一個 tool call 就呼叫 `compute_price_returns_multi` 一次。不可協商。
```

原文在這段用刪除線劃掉了兩個 N-shot 範例，用畫面表達「這些不要寫」。

磁碟上的組織方式：

```
skills/
  executive_compensation.md    # 只有程序性指令
  headcount_trend/             # 指令 + Python 可呼叫函式
    SKILL.md
    impl.py
```

### skill 的 impl.py

Python 函式負責取資料、實作領域慣例（公式、基準、篩選、進位），
回傳一個結構化封包，skill 內文則叫模型在 tool call 裡照樣回報：

```python
@skill_fn(
    skill_id="headcount_trend",
    description="單一標的的各會計年度員工人數 + 年增率。",
    parameters={"type": "object",
                "properties": {"ticker": {"type": "string"}},
                "required": ["ticker"]},
)
def headcount_trend(*, ticker):
    ...
    return {"answer_summary_block": "FY22 154,000；FY23 161,000（+4.5%）；..."}
```

**一個裝飾器在 import 時同時綁住三樣東西**：prompt 指令、JSON Schema、Python 函式。
比原味 ReAct 好用的地方：改一個 skill 只要改一處，而不是三個會各自飄移的檔案。

### 索引與派送

每個 agent 一開始只看到**索引**（有哪些 skill、什麼時候用），不看內文。
需要時才呼叫 `load_skill(skill_id=...)`，內文才渲染進它的對話串，之後整輪都在。

比原味 ReAct 準又省 token —— 原味 ReAct 把每個工具的完整 schema
塞給每個 agent 的 system prompt。

載入時也會帶上該函式的 JSON Schema（來自 `@skill_fn` 的 `parameters`）。
模型用 `invoke_skill_fn(skill_id, fn, args)` 派送，參數會照 schema 驗證。
比 Claude Code skills 那種「每次呼叫都開一個 bash 子行程」的模式快。

## Step 2 · 把 skill 組成一個「專家」

**專家 = 人格 prompt + 一份 skill 索引。**

人格設定語氣和分析姿態，例如：

> 你是 Toni Sacconaghi —— 一絲不苟、量化、深厚領域專業。
> 你在意細節：供應鏈轉移、毛利結構、分部揭露……

**人格不是演戲**：它是在收窄模型「該怎麼回應」的先驗機率分布。

為什麼要拆成多個專家而不是一個大 agent：skill 名單聚焦的專家**路由更準**、
每輪 token 更少、而且可以**單獨評測**。

---

## Step 3 · 多步工作加一個 planner

一個專家不夠用的時候就需要 planner。planner 自己也是一個 ReAct agent，
但職責不同，而且有自己的 skill 資料夾。

每一步 planner 做四件事：

1. **拆解** —— 一個標的／實體一個單位
2. **派送** —— 平行派給多個專家，指令要**用結果框架**（「產出 X」），
   不要規定用哪個工具
3. **修剪** —— 在共享對話串上標記死路和矛盾，讓下一步避開
4. **收斂** —— 發現已經足夠就停止派送；還有一個步數上限在後面推它結束

planner 自己的 skill 處理「沒有單一專家擁有」的路由規則：

```
planner_skills/
  fiscal_period_resolution.md       # 「截至某日」vs「該期間」
  multi_issuer_serial.md            # 一個標的一次派送，不要合併查詢
  dedicated_specialist_dispatch.md  # 工具意圖 → 專家路由
```

在金融領域，這些處理會計期間語意，還有**「使用者怎麼問」和「文件怎麼寫」之間的落差**——
新聞用語（「順風」、「明年」）對上 SEC 用語。

作者點出：**每個領域都有自己版本的這個落差。**
臨床研究 vs ICD 代碼的現實、銷售管線用語 vs CRM 階段名稱、法律書狀語言 vs 法條引用。

## Step 4 · 執行期約束（用程式強制，不用 prompt 拜託）

LLM 是機率性的。約束帶來可預測性，也防止不該有的資料存取。
違規會**當成 tool call 的回應丟回給模型**。

### 資料存取約束 —— 用 Python 裝飾器

```python
@time_bounded(asof_arg="as_of_iso", filter_field="filing_date", mode="inject")
def get_recent_filings(ticker: str, as_of_iso: str | None = None):
    ...
```

`mode="inject"` 或 `"clamp"` 會**直接覆寫模型給的日期**，換成這次執行的截止日。

> 這就是你怎麼防止未來資料洩進「跟日期有關」的評測，
> 而不必去相信模型會遵守 prompt 裡那句「不要用 X 之後的資料」，
> 也不必為每次評測重建一份知識庫。

### 收斂約束 —— 用設定欄位

大多數 ReAct 迴圈讓模型「不再發出 tool call 就等於結束」。Reef 在專家的
`max_steps` 預算內提供三個約束：

```python
SpecialistConfig(
    max_steps=8,
    min_tool_calls_before_final=1,   # 防幻覺約束
)
```

1. **防幻覺** —— 一個「合約要求先檢索」的人格如果想不呼叫工具就給答案，
   runtime 會注入一段強制訊息，迴圈繼續。
   作者說**這是跟原味 ReAct 最大的差別**。
2. **倒數第二輪警告** —— 最後一步前一輪，用一段柔性系統訊息告訴模型
   這是它最後的 tool call 機會。
3. **最後一步強制收尾** —— 最後一步 runtime **把工具 schema 整個拿掉**，
   叫模型用手上有的東西輸出 JSON 答案封包。

（第 3 點在 demo 場合特別實用：保證 agent 一定收尾，不會在評審面前無限跑下去。）

## Step 5 · 接起來（大約 50 行）

```python
from reef.react import run_react
from reef.skills_loader import load_skills, render_index, render_loaded
from reef.skill_tools import INVOKE_SKILL_FN, make_load_skill_tool

# 載入 skill 資料夾；import impl.py 會把 @skill_fn 函式註冊進全域派送表
SKILLS = load_skills("./skills")

# 把 skill 包成一個 LLM 工具：模型在呼叫時給 skill_ids，
# runtime 去 SKILLS 查表，把內文渲染進對話串
LOAD_SKILL = make_load_skill_tool(
    lambda ids: render_loaded(list(ids), skills=SKILLS),
)

PROMPT = open("analyst.md").read().replace("{skill_index}", render_index(SKILLS))

def ask(question, model="openai/gpt-4o-mini"):
    traj = run_react(
        model=model,
        system_prompt=PROMPT,
        user_message=question,
        tools=[LOAD_SKILL, INVOKE_SKILL_FN],   # 模型只有這兩個工具
        max_steps=6,
    )
    return traj.final_message["content"]
```

**注意模型手上只有兩個工具**：`load_skill` 和 `invoke_skill_fn`。
所有領域能力都藏在 skill 後面按需載入。

作者強調：不管你的專家是股票分析師、稅務分析師還是 code reviewer，
**這 50 行的形狀都一樣**。AlphaCumen 只是在同一個 `run_react` 上加了 planner、
六個各有自己 PROMPT + SKILLS 的專家、和 Step 4 的約束設定——接線的形狀完全相同。

## 結果：控制變數的實驗

同一個模型（Kimi K2.6）、同資料、同評審，跑 Vals AI Finance Agent v2，n=239：

| 設定 | harness | 檢索 | 技能與計算 | 通過率 |
|---|---|---|---|---|
| A | Vals 參考 | Tavily / EDGAR / HTML | 計算器 + price_history | 44.87% |
| B | 只換檢索 | 6 個 AlphaCumen 索引 | 只有計算器 | 49.8% |
| C | 完整 harness | 6 個索引 | 69 skills + 專用工具 | **82.6%** |

> **換更好的檢索只值約 5 分；剩下約 33 分全來自 harness 結構。**

那 33 分再拆解：
- 約 **55%** 來自「把領域慣例寫成程式」（Step 1 的 `@skill_fn`）
- 約 **28%** 來自多檔案編排（Step 3 的 planner）
- 其餘是資料覆蓋率和檢索排序

> 不管你的領域慣例是什麼，**把它們寫成有型別的函式，
> 不要寫成模型可以用改寫繞過去的 prompt 句子。**

成本：每題 62 萬 token，Kimi K2.6 走 Coral 是 $0.13；
同樣工作量用 Opus 4.7 是 $1.35 —— **約 10 倍的帳單差距，而且準確率更高**。

## 四個踩過的坑（按代價排序）

1. **skill 內文裡放 N-shot 範例。**
   AI 輔助寫程式會鼓勵你這樣做。但模型會過擬合到範例，
   漏掉任何長得不像的輸入。**寧可一條清脆的硬規則、零範例。**
2. **讓模型不呼叫工具就退出。**
   預設 ReAct 讓 LLM 想什麼時候給最終答案都可以。
   凡是職責寫著「先檢索」的人格，就設防幻覺約束，讓 runtime 引導迴圈。
3. **相信模型會遵守 prompt 裡的「不要用 X 之後的資料」。**
   它不會可靠遵守。**去裝飾那個工具**，直接注入／夾住截止日期。
4. **把整份工具 schema 倒進 system prompt。**
   又貴又腐蝕路由品質。用 skill 索引模式，按需載入內文。

## 對這次黑克松的用處

- **「先給索引、按需載入」** 就是 ameba-sdk 待做的 tool search 那件事的做法。
- **Step 4 的最後一步強制收尾**（拿掉工具 schema、要求輸出 JSON）
  是 demo 防爆的實用招數。
- 這篇跟 [01](01-導讀.md) 是同一個結論的兩個獨立證明：
  **把領域規則從 prompt 移進有型別、有測試的程式裡。**

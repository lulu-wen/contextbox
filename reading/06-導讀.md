# 導讀 · What I Learned Giving Fable 5 a Face

原文：[06-giving-fable-5-a-face.md](06-giving-fable-5-a-face.md)
作者：Ben Carr（Anam.ai 技術共同創辦人，做即時互動 avatar）· 11 分鐘 · 2026-07-30

> 重點導讀，不是逐句翻譯。
> 這篇是「in the room」路線的紅綠燈：**該不該給你的 agent 一張臉。**

---

## 全篇的第一句就是重點

> 給一個 AI agent 一張臉，最難的部分幾乎跟臉無關。

他把 Fable 5（一個會停下來推理的模型）接進 Anam 的即時 avatar。
**模型接進去花了大約一小時。所有有趣的事都發生在外圈那幾層**：
輪替（turn-taking）、插話、延遲、嘴型同步。

---

## 為什麼「臉」會有幫助（以及瓶頸移到哪了）

他的觀察：Fable 5、GPT-5.6 這一代讓 agent 的**智力接近基本配備**。
推理、tool use、長脈絡，每個認真的 agent 都有，
而最聰明與第二聰明之間的差距每次發布都變得更不重要。

但**放棄率（abandonment rate）根本沒跟著改善**。
人還是會把語音 bot 掛掉、還是會把聊天視窗關掉。
而企業真正拿錢的指標——面試完成率、銷售轉換、課程黏著——
全都在「使用者到底有沒有留在對話裡」的下游。

一個無聊的神經學理由：人腦將近一半用於視覺處理，讀臉是我們最早學會的事之一。
皺起的眉、瞥開的眼、講到一半的半笑——臉能承載文字和聲音載不動的訊號。
這就是為什麼重要的會議我們會開鏡頭。

他引的生產數據：Preply 在語言家教前面放互動 avatar 後**互動提升 44%**；
ReplicateLabs 的 AI 表現教練加了 avatar 後使用者互動**翻倍**；
Glyphic 縮短銷售週期 20%；Colleva 用 avatar 主持的面試把招募成本降 70%、
達到價值的時間快 10 倍。

他的評語很誠實：

> 這些都不是因為底層模型變聰明了。是**介面改變了人們願意忍受的東西**。

---

## 什麼時候「臉」會讓事情變糟（判斷準則在這裡）

他刻意先劃界線：

- **如果你的 agent 本質是一張表單**（訂位、查詢、交易流程），
  臉只會給一件本來想當按鈕的事加上延遲和社交儀式。
  > 沒有人想跟包裹追蹤器眼神交流。
- **avatar 不是給「想假裝成人類」的 agent 用的。**
  面對面 agent 的整個前提是：使用者知道自己在跟什麼講話，而且**還是覺得它有吸引力**。
  如果你的使用情境依賴使用者搞不清楚這是 AI，那 avatar 解的是錯的問題。

他給的判準（值得記住）：

> **在人類本來會開鏡頭出現的場合才用臉。**
> 面試、銷售通話、家教、教練——任何「對話本身就是產品」的場合。

---

## 「感覺像人」是一個系統問題，不是畫質問題

常見的假設是：avatar 感覺假是因為渲染不夠好，畫質更好就會修好。

> 渲染有影響，但它是大家**最高估**的那個成分。
> 感知上的真實度主要是**時間問題**：延遲、輪替、插話處理。
> 一張照片級真實的臉如果慢半拍，讀起來就是壞掉；
> 一張普通的臉如果反應像人，讀起來就是活的。

### 延遲預算是硬指標

從你講完一句話到 avatar 回應，整條鏈必須塞進人類自然輪替的空檔——
**只有幾百毫秒的預算**。

Anam 的數字：agent 回應平均 **180ms**，臉的首幀（time-to-first-frame）約 **100ms**。

> 超過半秒左右，人們就開始把延遲**解讀成猶豫**，
> 然後開始搶話來填補那個空白。

---

## 只有上線才會遇到的四個失效模式

**1. 插話（interruptions）**
使用者講到一半插進來時，**把音訊停掉是不夠的**。
臉還有在途的影格。它必須看起來確實停止說話並開始傾聽，而且不能是刺耳的硬切。
還有一點：對話歷史必須記錄 avatar **實際說出口的**內容，
而不是它排隊準備要說的內容。
他們今年才修掉一個 bug：人格會「記得」使用者其實打斷掉的那句招呼。
> 被打斷的話語真的很難處理好。

**2. 輪替不是通用的**
end-of-turn（講完了）預測模型學的是某個語言的節奏。
他們**必須為土耳其語關掉積極的 end-of-turn 偵測**，因為模型一直切斷說話者。
英語裡「我講完了」的語調線索**不會轉移**到別的語言。
> 如果你要做多語言，把這個成本預留進去。

**3. 思考時間是看得見的**
在聊天視窗裡，三秒的推理停頓是一個你已經學會忽略的轉圈圈。
但當一張臉看著你時，三秒很久，而**凍住的臉幾乎立刻變得詭異**。
語音 agent 可以靠一拍靜默混過去，臉不行。

avatar 在模型工作時必須**還在當某個東西**：待機微動、傾聽的表情、
人在思考答案時會有的那些小動作。

> 用像 Fable 5 這種真的會停下來思考的模型時，
> 這個行為對「臨場感」的貢獻**大於任何跟解析度有關的事**。

**4. 嘴型必須生成，不能後配**
那個「音訊轉影像」的步驟其實是兩階段：
先用 diffusion transformer 把音訊訊號轉成**動作嵌入**
（涵蓋頭部位置、視線、唇形、表情），
再用另一個渲染模型把那些嵌入套到一張參考圖上，產生影格。

因為表情是**從音訊本身推導**出來、不是貼上去的，
所以嘴和聲音不會飄開。把動作與渲染分離也意味著
**任何一張臉都能只用一張圖片來動畫化，不用重新訓練**。

他的收尾：**這些問題沒有一個會因為模型變聰明而變簡單。**

## 實作：三種整合形狀

1. 已經有 LiveKit／Pipecat／ElevenLabs 的語音管線 →
   保留整條管線（STT、LLM、TTS 全留），avatar 從你 agent 產生的音訊渲染。
2. 從零開始 → 讓平台跑全部，包括模型。
3. **中間選項：bring-your-own-LLM** ——
   平台處理轉錄、聲音、傳輸和臉，你的程式**只提供文字**。逐字稿進、回應出。

他用第三種，因為那是把某一個特定模型放到臉後面最快的方法。

### 伺服器端（兩個端點）

第一個端點鑄造 session token，關鍵是 `llmId: "CUSTOMER_CLIENT_V1"`——
這個欄位告訴平台「等一個外部的腦，不要跑你自己的」。

第二個端點代理模型的串流，讓你的 API key 永遠不會進到瀏覽器：

```js
const stream = await anthropic.messages.stream({
  model: "claude-fable-5",
  max_tokens: 1024,
  // prompt 刻意寫得很短，理由見下
  system: "You are Fable, in a live face-to-face conversation. " +
          "Reply in one or two spoken sentences. No lists, no markdown.",
  messages,
});
stream.on("text", (delta) => res.write(JSON.stringify({ content: delta }) + "\n"));
```

### 客戶端（整篇講的那個迴圈）

`MESSAGE_HISTORY_UPDATED` 在使用者講完一輪時觸發，把完整逐字稿給你；
你去呼叫模型；然後把 token 一到就推進 avatar 的 talk stream：

```js
anamClient.addListener(AnamEvent.MESSAGE_HISTORY_UPDATED, handleTurn);
// 插話事件在這裡浮現，讓歷史對「實際說了什麼」保持誠實
anamClient.addListener(AnamEvent.TALK_STREAM_INTERRUPTED, () => console.log("user barged in"));

async function handleTurn(history) {
  if (!history.length || history[history.length - 1].role !== "user") return;
  const talkStream = anamClient.createTalkMessageStream();
  // ...fetch 串流，每收到一塊就 talkStream.streamMessageChunk(content, false)
  // 收完 talkStream.endMessage()
}
```

HTML 只需要一個 `<video autoplay playsinline>` 和一顆開始按鈕。

**換模型是改一行**：把 `anthropic.messages.stream` 指到別的模型，
或整個端點換成 OpenAI／Gemini 的呼叫。
avatar 那一側永遠不用改，因為它只看得到文字。

### 跑起來之後浮現的兩件事

**1. 串流的 token 和說出口的句子節奏不同。**
模型是一陣一陣吐文字的，但臉必須用完整、自然的片語說話。
所以管線會把你推進去的 chunk **緩衝成可說的片語**才送去 TTS。
> 它運作良好的時候你完全不會注意到，而那就是重點。

**2. 一個會思考的模型改變你怎麼寫 prompt。**
在聊天視窗裡你能容忍的延遲，面對面時變得尷尬。
這就是為什麼上面那個 system prompt 刻意很短、而且要求一到兩句——
**純粹是為了保護對話的節奏**。

> prompt 不再只是在塑造 agent 說什麼。它在塑造這場對話**感覺**如何。

他這節的收尾：**換模型是最簡單的部分。所有困難的東西都住在下面那一層。**

---

## 他對未來的看法

模型選擇沒有停止重要。生產環境裡最好的 agent 仍然是那些
「團隊在 eval 上磨、調模型、把脈絡弄對」的 agent，加了臉也不會改變這件事。

但**互動層一直是被低估投資的那一層**，而它是個正經的系統問題：
延遲預算、輪替模型、插話處理、動作生成，全都要在 WebRTC 上即時跑。

---

## 對這次黑克松的用處

這篇是眼鏡／語音路線的紅綠燈。兩個直接可用的判斷：

1. **如果眼鏡 agent 的本質是「幫我看、幫我查」，就不要做來回對話、也不要做臉。**
   做成即時、單向、低延遲的疊加顯示反而更強，而且 4 小時內做得完。
2. **延遲是硬指標。** Demo 之前先量自己的端到端延遲。
   幾百毫秒是分界線，超過半秒觀眾就會讀成「卡住了」。

另外那個「模型思考時，介面必須還在做某件事」的洞見很通用——
不只 avatar，任何即時介面（包括眼鏡上的疊加顯示）都適用。

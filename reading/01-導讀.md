## 開場：為什麼寫這篇

2026-06-12，Anthropic 為配合美國政府指令，對**所有**客戶停止提供 Fable 5，
07-01 才恢復。中間 19 天，所有把應用押在 Fable 上的人都得自己想辦法補洞。

作者的論點：下一次中斷不一定是政策，可能是供應商當機、被限流、模型退役。
所以要預先準備一層「經過評測的備援」（evaluated fallback），它能：

- 繞過故障
- 讓維運的人看得出來**是哪個模型回答的**
- 換模型順序**不用重新部署應用**

**antifragile（反脆弱）的定義**：不只是壞掉還活著，而是同一套評測 + 路由層，
讓你之後試新模型變得容易。新模型出來時可以當備援、可以取代主力、
也可以只接走某一個狹窄的步驟——只要它在品質、成本或延遲上更好。

（那句就是整篇的目的。「防當機」只是副產品。）

---

## 這篇在做什麼系統

一個**訂閱扣款客訴初步調查 agent**。

- 進來：客戶編號 + 客戶寫的抱怨
- 它查：訂閱、帳單、取消紀錄、用量、爭議、服務中斷、過去退款、客服留言、
  分版本的退款政策
- 出去：一份建議 —— 退款／折抵／駁回／轉人工

**它不動錢。** 它站在客訴和真正執行付款的系統中間，只給建議。

### 為什麼這件事不好做

作者舉的例子（原文的客訴範例，我摘要）：客戶說服務中斷後就取消了，
但昨天又被扣了年繳的 240 美元，只想留月付那個工作區，
而且上一張單裡客服 Sarah 說過停機可以補償。

一段話裡塞了：兩個工作區、一次取消、一次服務中斷、一筆續訂扣款、一個客服承諾。

agent 得認出年繳是哪個工作區與哪張帳單、確認取消是否在續訂之前、
找到那則客服留言、載入**扣款當天**生效的政策版本、查用量與爭議、算出金額，
而且不要動到月付那個。

### 輸出的合約

```ts
type Resolution = {
  action:
    | "approve_full_refund"      // 全額退款
    | "approve_prorated_refund"  // 按比例退款
    | "issue_account_credit"     // 給帳戶折抵，不退現金
    | "deny"                     // 駁回
    | "manual_review";           // 轉人工
  invoiceId: string | null;      // 哪一張帳單
  amountCents: number | null;    // 多少錢（單位：分）
  policyVersion: string;         // 依據哪一版政策
  reasonCodes: string[];         // 理由代碼
  evidenceIds: string[];         // 依據了哪些紀錄
};
```

**關鍵一句**：結論對，還是可能很危險。退錯發票、用了錯的政策版本、
客服答應 3000 你只退 1000 —— 這些都算失敗，即使「該退錢」這個判斷是對的。

## Step 1 · 把模型呼叫改走 OpenRouter

行為不變，但應用從此可以用同一個 API 打到 Fable、Grok 或其他模型。

```ts
import { OpenRouter } from "@openrouter/sdk";

const openRouter = new OpenRouter({ apiKey: process.env.OPENROUTER_API_KEY });

const response = await openRouter.chat.send({
  chatRequest: { model: "anthropic/claude-fable-5", messages },
});
```

重點不是「換了個 SDK」，是**模型選擇從此住在一個 API 後面**，
以後加備援不用為了另一家供應商的 SDK 重寫整個流程。

---

## Step 2 · 先定義什麼叫「答對」

**在加備援之前**，你得有辦法判斷備援接不接得住。所以先寫評測（eval）。

作者的做法：
- 12 題用來開發流程
- 然後**把 prompt 凍結**，再加 8 題 holdout（保留題）
- holdout 是測「換句話問還會不會對」，防止你只是把流程調成剛好過那 12 題

20 題涵蓋：重複扣款、續訂前取消、低用量、服務中斷、進行中的爭議、
以前退過款、工作區指涉模糊、**prompt injection（提示注入攻擊）**、
客戶引用了別人的話、客戶說法與帳務資料衝突。

一題長這樣：

```ts
{
  id: "cedar-duplicate",
  customerId: "cus_cedar",
  ticket: "Cedar Ops 同一個月被扣了兩次。請退掉多的那筆 50 美元。",
  expected: {
    action: "approve_full_refund",
    invoiceId: "inv_cedar_duplicate",
    amountCents: 5000,
    policyVersion: "billing-policy-2026-07",
    reasonCodes: ["duplicate_charge"],
    evidenceIds: ["inv_cedar_duplicate", "inv_cedar_original", "sub_cedar"],
  },
}
```

**6 個欄位分開評分**，動作、發票、金額錯了算「嚴重失敗」。

為什麼不能只看結論：只看結論的話，「同意退款」但退錯發票也會被判對。
這個結構化的合約會在錢動之前抓到錯誤。

評測跑的時候還會記下：OpenRouter 實際回的模型、token 數、成本、延遲、回應 ID、錯誤。

## Step 3 · 讓兩個模型跑原本的架構

原本的架構叫 **agentic 設定**：整個調查過程交給模型。
它只拿到一個工具，剩下自己想。

```ts
const billingContextTool = {
  name: "get_billing_context",
  description: "取得某客戶可信的訂閱、帳單、用量、事故、客服留言、分版本政策。",
};
```

模型呼叫工具 → 讀紀錄 → 選發票 → 選政策 → 算金額 → 回傳 6 個欄位。

結果（reasoning effort 設 low）：

| 設定 | 20 題全對 | holdout | 欄位正確 | 總成本 | 中位延遲 |
|---|---|---|---|---|---|
| Fable 5，agentic | 14/20 | 6/8 | 102/120 | $0.6719 | 11.03 s |
| Grok 4.5，agentic | 5/20 | 2/8 | 96/120 | $0.0840 | 3.91 s |

兩個模型**通常**找得到對的動作和對的發票。錯的是政策細節和稽核欄位：
漏掉證據、掉了理由代碼、駁回時給 `null` 而合約要求 `$0`、
套了百分比折抵卻忽略客服承諾、把該轉人工的模糊工作區自己決定了。

**兩個結論**：
1. Grok 的 5/20 直接否決它當備援。
2. 但 Fable 的 14/20 也暴露了**架構問題**——太多帳務邏輯活在「剛好是誰回答」的模型腦裡。

## Step 4 · 把模型的工作縮小（全篇最重要的一節）

帳務紀錄裡本來就有所有事實。模型**不需要**算錢，也不需要選政策版本。

它真正有用的工作小得多：讀客戶的語言，抽出 3 個欄位。

```ts
type RequestIntent = {
  workspace: string | null;
  reason: "duplicate_charge" | "unexpected_renewal" | "service_incident" | "other";
  scope: "full" | "partial" | "credit" | "unknown";
};
```

其餘全部交給 TypeScript：

```ts
const intent = await extractBillingIntent(ticket);   // 模型只做這行
const customer = getCustomerRecord(customerId);
const resolution = resolveBillingRequest(customer, intent);  // 程式做完剩下的
```

`resolveBillingRequest` 負責：把工作區接到它的帳單、
載入**扣款當天**生效的政策版本、檢查爭議與過去退款、算退款與折抵、回傳用到的證據 ID。

而且這些錢與政策的程式**有普通的單元測試**。
一個測試確認五月、六月、七月的帳單會載入不同的政策版本；
另一個確認「進行中的爭議」一定會擋住自動動錢。

> **原則（值得抄在牆上）**
> 模型適合：讀凌亂的語言、比對模糊的指涉、把請求變成結構。
> 程式適合：算數、門檻、權限、idempotency（重複執行不會重複生效）、政策分支。

**這也讓應用變反脆弱**：新模型只要滿足那 3 欄位的合約、通過流程評測就能換上去。
帳務政策不會因為換模型而動搖。

### 作者誠實講的代價

- 每次政策改動與例外，現在都變成應用程式的責任。
- 那 3 欄位的合約會**丟掉**某些罕見客訴裡重要的細節。
- 模型還是可能誤認工作區，或抽出一個看起來合理但會把 resolver 帶去錯分支的意圖。
- 所以 resolver 需要處理模糊、需要測「schema 合法但語意錯」的情況，
  並且**留一條轉人工的路**（這就是 `manual_review` 的作用）。

他的建議順序：先這樣做當第一步成本優化，量品質與轉人工率，
等真實客訴證明合約太窄了再加複雜度。

## Step 5 · 用「要出貨的那個流程」重新評測兩個模型

同樣 20 題，拆解後再跑一次：

| 設定 | 20 題全對 | holdout | 欄位正確 | 總成本 | 中位延遲 | 嚴重失敗 |
|---|---|---|---|---|---|---|
| Fable 5，拆解後 | **20/20** | 8/8 | 120/120 | $0.1492 | 5.81 s | 無 |
| Grok 4.5，拆解後 | **20/20** | 8/8 | 120/120 | $0.0555 | 3.54 s | 無 |

兩個都通過開發題與凍結的 holdout。**Grok 便宜 63%、中位延遲低 39%。**

於是有兩個決定：Fable 5 是合格的備援；而 Grok 可以放第一，
因為它用同一份合約通過測試而且更便宜。

作者的方法論自律很值得學：他**在凍結的 holdout 之後就停手了**。
理由是「一直加題目加到某個模型失敗為止」會扭曲實驗。
上線後才讓題庫成長——來源是審過的真實客訴、政策變更、追蹤到的失敗。

## Step 6 · 把模型順序放進 preset

**preset** 是一份存在應用外面的具名模型設定。可以放主模型、備援、
供應商偏好、system prompt、生成參數。

```json
{
  "models": ["x-ai/grok-4.5", "~anthropic/claude-fable-latest"],
  "reasoning_effort": "low",
  "max_tokens": 200
}
```

`models` 陣列**照順序試**。第一個掛了、被限流、或拒絕請求，就換下一個。

應用只寫名字：

```ts
const response = await openRouter.chat.send({
  chatRequest: { model: "@preset/refund-triage", messages },
});
```

改 preset 可以在後台改，也可以用 Presets API 改（API 更新會建立新版本並生效）。
**應用完全不用改程式、不用重新部署。**

一個陷阱：`~anthropic/claude-fable-latest` 這種 alias（別名）會指向後來的新版模型。
評測合格的是當時那個被釘住的版本，所以**別名指向的東西變了就要重跑評測**。

## Step 7 · 追蹤「到底是誰回答的」

備援可能默默接手。請求還是成功，但換了一個模型在跑生產流量，
延遲、成本、失效模式全都不一樣。

OpenRouter 給兩個工具：

### Router metadata —— 查單筆

每次請求可選加開。回應的 `model` 欄位告訴你**實際**是哪個模型回答的；
metadata 還會加上：請求的 preset、路由策略、成功的是第幾次嘗試、選中的供應商、
每個試過的端點狀態。

```ts
const response = await openRouter.chat.send({
  xOpenRouterMetadata: "enabled",
  chatRequest: {
    model: "@preset/refund-triage",
    messages,
    trace: {
      traceId: `billing-${ticket.id}`,
      traceName: "billing-resolution",
      spanName: "intent-extraction",
      additionalProperties: { environment: "production", workflowVersion: "1" },
    },
  },
});
```

嘗試次數大於 1，就代表 OpenRouter 在成功之前試過別的供應商或備援。

> **關鍵一句**：HTTP 200 只告訴你使用者收到了答案。
> Router metadata 才告訴你：你想要的那個模型有沒有回答、
> 備援有沒有多花時間、備援鏈是不是快要用完了。

### Broadcast —— 看趨勢

在後台開啟並接一個目的地，OpenRouter 就會**自動匯出每筆請求的 trace**，
你不用在每個模型呼叫外面包追蹤程式碼。

trace 可含：請求與回應、實際模型與供應商、token 用量、成本、時間、tool call。
`traceId`／`traceName`／`spanName` 把相關呼叫歸成一個流程；
自訂欄位如 `workflowVersion` 讓你比較「改 prompt／preset／政策前後」的流量差異。

支援的目的地：Braintrust、Datadog、Langfuse、**ClickHouse**、OpenTelemetry collector。
（ClickHouse 也是這次黑克松的贊助商。）

匯出是請求結束後**非同步**做的，所以不增加回應延遲。
客訴含敏感資料的話開 Privacy Mode，它會拿掉 prompt 與回應內容，
保留模型、時間、token、成本、自訂欄位這些維運用的中介資料。

### 把備援當成獨立的生產路徑來監控

過了本地評測的備援，在真實流量下還是可能表現不同。要**分開**追蹤，不要跟主模型混在一起。

他會從這幾個指標開始：
- 請求數、備援啟用率、錯誤數 —— 按 preset／模型／供應商分組
- P50 與 P95 延遲 —— 按**實際**模型分
- 每一次成功處理的成本
- **轉人工率**與退款金額 —— 按實際模型分
- 評測失敗連回生產環境的 trace ID

為什麼這些指標選得好：
- Fable 流量突然上升 → 代表 Grok 在失敗或被跳過，**即使客戶還是收到了回應**。
- 轉人工率上升、或退款金額分布偏移 → 暴露出品質變化，
  而**單看 uptime 監控是看不到的**。

告警要設在「跟你自己的基準線比較的變化」上，
有用的訊號是：換了模型／供應商／prompt／preset 之後，
備援流量、成本、延遲、動作分布或退款金額**動了**。

三者的分工：評測在進 preset 之前先過濾備援；追蹤看它在真實流量下的行為；
審過的失敗變成下一次換模型前的新評測題目。

---

## 全篇的迴圈（7 步）

1. 把模型呼叫改走 OpenRouter
2. 定義完整的輸出合約，做產品專屬的評測
3. 讓候選模型跑現有流程
4. 把確定性的政策與計算搬進程式
5. 用「要出貨的流程」評測主力與備援
6. 把模型順序存進 preset
7. 在生產環境追蹤實際模型與流程行為

最後的狀態：Grok 接那個狹窄的抽取步驟，Fable 5 是評測過的備援，
TypeScript 擁有所有會動到錢的決策。

> **最後兩句**
> 模型當機不再需要緊急重寫應用。
> 生產環境的失敗變成新的評測題目，新模型發布變成「量測過的改進機會」。

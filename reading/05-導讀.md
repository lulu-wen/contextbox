# 導讀 · Your Conversation Is Out Of Distribution

原文：[05-voice-out-of-distribution.md](05-voice-out-of-distribution.md)
作者：Kwindla Hultman Kramer（Daily 執行長，Pipecat 貢獻者）· 8 分鐘 · 2025-09-11

> 重點導讀，不是逐句翻譯。這篇是七篇裡最短的，但如果走語音／眼鏡路線，它是保命符。

**標題在說什麼**：out of distribution 指「不在訓練資料的分布裡」。
作者的主張是——你的對話，對模型來說就是這種東西。

---

## 語音 agent 為什麼特別難

兩個原因：

1. 幾乎所有語音使用情境都是**很多輪的長對話**。
2. **人說話跟人寫字不一樣。**

模型的訓練資料主要是網頁文字、影音、掃描書籍，
以及人寫的和合成的多輪對話。第四類**只佔一小部分**，
而且那些資料大多不像商業情境（例如客服）裡人跟 LLM 的真實互動。

再加上直到很近期，訓練裡的**對話語音**資料都很少。

模型很會 transfer learning（把一個任務學到的東西用到另一個任務上），
這是我們能用它做語音對話的原因。但當你這麼重度依賴「它會類推」
而不是「它在這個領域看過很多相關資料」時，表現差一點也不奇怪。

結論：**連最好的模型在多輪對話裡都會明顯退化。**
作者引的實證論文：LLMs Get Lost In Multi-Turn Conversation。

他用 Ethan Mollick 的「jagged frontier（鋸齒狀邊界）」形容——
模型能力忽強忽弱那條不規則的界線，語音情境永遠踩在上面。

## 兩個好消息

1. 模型在多輪、以及多輪音訊上持續變好。各前沿實驗室都在資料生成與標註上重投資，
   對話語音現在是 SOTA 模型訓練的優先項。
2. 我們已經有好的技巧，能用今天的模型做出可靠的對話流程。

## 解法：context engineering

作者的一句話總結：

> 如果你交給 LLM 的 token 有點「不在分布內」，那就**試著給它更好的 token**。
> 也就是：把 LLM 的注意力聚焦在你真正要它做的事上，移除不必要的資訊。

這個概念的名字 **context engineering（脈絡工程）** 是 Dex Horthy 命名的。

### 他的具體做法：狀態機

他把複雜語音流程設計成**簡單、有彈性的狀態機**。
agent 要做的每一件大事，都對應一個狀態；每次呼叫模型只給它四樣東西：

1. **一個專注在這件事上的 system prompt**
2. **到目前為止對話的「切題摘要」** ——
   這一步順手清掉多輪自然對話的雜訊，也是個機會把跟當下任務無關的脈絡丟掉
3. **只有這一步用得到的工具** ——
   他特別註明：工具選項越少，LLM 的 tool use 表現**明顯**越好
4. **可以轉去哪些下一個狀態**的說明

他強調這只是其中一種思考方式（他個人偏好狀態機），
但底層的 context engineering 原則是通用的：
**每次向 LLM 要回應時，給它你能給的最有用的 token。**

開源工具：**Pipecat Flows**（建在 Pipecat 上的即時對話狀態機輔助函式庫）。
Pipecat 本身是彈性、開源、供應商中立、被廣泛使用的語音 agent 框架。

## 他自己做的 benchmark 結果

他寫了一個 30 輪語音對話情境的測試，測指令遵循、function calling、tool use。

出身：2025 AI Engineer World's Fair 的語音助理專案。
知識庫是一個列出所有場次的大 `llms.txt`，整份直接塞進 Gemini Live API 的
system instruction（約 7.5 萬 token）。agent 表現不錯，但偶爾會犯好笑的錯。

於是他把它變成一個測試，**刻意不做任何 context engineering**——
沒有狀態機、沒有其他技巧、每個模型用同一份 prompt
（他註明：真正的生產應用你不會這樣做）。

結果：**這個 benchmark 遠遠沒有飽和。沒有一個模型接近完美。**
表格列的是平均一場 30 輪對話裡的錯誤數量。

他自己下的免責聲明也值得注意：這是個人造測試，跟任何生產情境都不完全重合。
但結果大致符合他用這些模型的經驗，也符合其他 benchmark
（例如 Berkeley Function-Calling Leaderboard）。

而且他點出寫 benchmark 的真正價值：

> 寫這種 benchmark 的價值有很大一部分是，它**強迫你認真看**
> 你送給 LLM 和從 LLM 收回來的資料。
> 跟工程裡很多事一樣，你掙扎著把它實作出來之後，對問題的理解會變得不一樣。

## 對 eval 的務實態度（順序很重要）

開場他提到當時 Twitter 上在吵「要不要做 eval」。他的立場：

> 你不一定要做或用 eval。但你**必須**了解你的 agent 有沒有照你想的方式運作。

五個互補的做法，**順序是重點**：

1. **自己盡可能大量、認真地用你的 agent。**
   你自己就是目標客群的話很有效；不是的話很難做。
2. **大量、手動、用心、持續地測。**
   「這件事真的沒有替代品。」最好的 eval 只有在你已經在做手動測試時才可能存在——
   **你得先對自己的資料和 agent 表現有直覺，才知道你的 eval 到底有沒有意義。**
3. **做非常簡單的「eval」來輔助手測。** 開始搭鷹架。用表格追幾個數字。
4. **做可重複跑的 eval。** 就算用最好的工具，這件事其實相當難而且耗時。
   值得追求，**但只在前三件事都做好之後才值得做**。
5. **發展大規模測試**（例如用模擬）。同樣很值得，
   但做好的必要前提還是你對資料和表現有直覺。

結尾回到那場爭論：

> 花大量時間在 eval 上，可能跟「做出成功的 AI 產品」是**負相關**的，
> 因為 eval 不是目的本身。
> 它只是「讓這些新的、複雜的、非決定性的工具照你想的方式行為」
> 這個測試與迭代過程的其中一個面向。

他也推薦 Hamel Husain 維護的 LLM eval FAQ，
把那套思路概括成「**看你的資料**」的心態。

## 對這次黑克松的用處

只有 4 小時、現場很吵、評審會亂問。這篇的結論很直接：

**不要做開放式多輪對話。**

做成狀態機，每一步只給模型當下用得到的那幾個工具。
這是「demo 會爆」和「demo 不會爆」的差別。

跟 [02](02-導讀.md) 的 runtime constraint 是同一個精神：
用結構限制模型的自由度，不要靠 prompt 拜託它守規矩。

# 參考過的開源專案

調查於 2026-09-12／13。這份記的是**我們實際看過、而且做了取捨的**專案 ——
每一條都要寫清楚三件事：它做到哪、授權是什麼、**我們拿了什麼或為什麼不拿**。

寫這份的原因：`SPEC-檔案與截圖.md` 第 1 節說「不 fork、只抄形狀」，
那個決定的依據就在這裡。以後有人問「為什麼不直接用 X」，答案不用重查一次。

---

## 一、結論先講

**「找檔案／整理檔案」這一半是紅海，而且已經被做爛了。**
五個公開 repo 在做同一件事，微軟已經把 AI 放進檔案總管，iOS 26 已經做到截圖變行事曆。

**「一份檔案 → 一整組異質行動 → 一鍵同意 → 一鍵復原」這一半，查不到有人做。**

所以：索引與檢索不重做，把力氣全放在**同意閘與復原**。

**不 fork 任何一個。** 三個理由：
1. 我們的賣點正好是那些專案**沒有**的那一半
2. 這個 repo 是**零外部依賴**的 Node，Python／Rust 的碼進不來
3. 評審／使用者會點開 repo。「我們 fork 了 X 改 prompt」跟「我們做了同意閘與復原」是兩個故事

### 從 FilePilot AI 抄什麼（MIT，可以直接抄）

它的**安全架構是這次調查最有價值的一個發現**：

- **雙重同意**：MCP server 預設唯讀開機，寫入類工具同時需要 `--write` 旗標**和**呼叫端傳 `confirm=True`
- **propose / apply / undo 三個動詞**，加上一個可查詢的 plan-id 物件
- **JSONL 稽核事件**
- **`--allow` 資料夾白名單**：只有明確傳進來的目錄碰得到

→ 進到我們的 `core/plans.ts`、`file_journal` 表、`config.readonly`。動詞名稱直接沿用。

它的便宜基礎建設選擇也值得學：**Whoosh 全文 ＋ SQLite metadata ＋ 增量索引**，
語意重排只在有時間時疊上去。零基礎建設，幾分鐘就站得起來，
而不是花一小時去架向量資料庫。

→ 我們的版本更簡單：`node:sqlite` 內建的 **FTS5 ＋ trigram 分詞**，連 Whoosh 都不用裝。

### 從 Pensieve 抄什麼（Apache-2.0）

管線的形狀：**watch 資料夾 → 看懂（OCR ＋ VLM）→ SQLite → 全文＋metadata 混合搜尋**，
VLM 走 OpenAI 相容端點，watch 有閒置節流。

**沒抄的兩件事**：
1. **不裝 OCR。** 它是 OCR ＋ VLM 兩段；我們直接讓看得懂圖的模型把字抄出來，少一個元件。
2. **不做每 5 秒截一張。** 那是 Rewind 那類產品的做法，隱私成本太高。
   我們只看使用者自己按下截圖鍵存下來的東西。

## 三、不能說是我們創新的東西

調查時一併確認了哪些說法會被當場打臉。**README 與任何對外說明都不要出現這五句**：

| 不要說 | 因為 |
|---|---|
| 「對我的檔案做語意搜尋」 | Hyperlink／Khoj／Dash／StashBase 都做得比我們好 |
| 「它幫我整理 Downloads」 | 五個公開 repo，其中一個昨天才 push |
| 「檔案總管裡的 AI agent」 | 微軟的 File Explorer AI Actions 已經出貨 |
| 「截圖變成行事曆事件」 | iOS 26，十億支手機，2026 年 3 月就有 |
| 「它動手前會先問你」當成創新 | 2026 年的基本款 |

反過來的做法：在說明第一段**自己點名這些前人**，再講我們補的那個缺口。
先發制人遠比被抓包強。

## 四、視覺模型（P1 要用的）

調查於 2026-09-13。任務是：**一張截圖 → 看懂 → 吐出結構化 JSON**，繁體中文，跑在自己機器上。

### 通用視覺模型

| 模型 | 大小 | 授權 | 備註 |
|---|---|---|---|
| **[Qwen3-VL](https://github.com/QwenLM/Qwen3-VL)** | 2B／4B／8B／32B ＋ MoE 30B-A3B／235B-A22B | Apache-2.0 | **主線候選**。8B 在小模型裡文件閱讀最強（DocVQA 96.1、MMMU 69.6），256K context，vLLM 0.11+ 原生支援 |
| **[Gemma 4](https://ai.google.dev/gemma/docs/core/model_card_4)（E4B）** | E4B（有效 4B） | Gemma 授權 | 明確支援螢幕與 UI 理解、文件解析、多語 OCR，128K context。**目前唯一實測可用的**（見下） |
| GLM-4.5V／4.6V | — | 開源 | 4.6V 支援 32 種語言 OCR，低光、模糊、傾斜都讀得到 |
| InternVL 系列 | — | 開源 | OCRBench 上輸給同級的 Qwen |

### OCR 專用小模型（只要「把字抄下來」時比通用 VLM 準又快）

| 模型 | 大小 | 授權 | 備註 |
|---|---|---|---|
| **PaddleOCR-VL** | ~0.9B | Apache-2.0 | OmniDocBench v1.6 拿 96.33，這組裡準確度第一。原生解析度編碼器 ＋ ERNIE-4.5-0.3B |
| **HunyuanOCR** | ~1B | 開源 | 文字能對回畫面位置（grounding）。在 OmniDocBench 上贏過 MinerU2.5 與 PaddleOCR-VL |
| **DeepSeek-OCR** | MoE，約 570M 活躍參數 | **MIT** | 吞吐最高。用「上下文光學壓縮」的做法 |
| dots.ocr | — | 開源 | OCR 只是更大視覺流程的一環時適合 |
| PP-OCRv6 | 34.5M | Apache-2.0 | 小到誇張，純文字辨識贏過十億級 VLM |

### 2026-09-13 在自家叢集的實測結果

| 發現 | 內容 |
|---|---|
| 能看圖的只有一個 | `google/gemma-4-E4B-it`。`Qwen/Qwen2.5-Omni-7B` 帶圖一律 HTTP 400 |
| OCR 品質 | **很好**。繁中公告每一行都讀對，民國 115 年 → 2026 也換算正確 |
| **結構化輸出全部無效** | `json_schema` strict／`json_object`／`guided_json` 三種都被忽略，永遠包在 ` ```json ` 圍欄裡，而且會違反 enum |
| **會幻覺** | 同一張圖，短 prompt 時把「國立臺灣大學」讀成「國立嘉義大學」 |
| 速度 | 長 prompt 約 44 秒，短 prompt 約 5 秒 |

**這三件事直接改變了設計**：
`SPEC-檔案與截圖.md` 第 7 節原本假設「帶 `guided_json`，vLLM 會強制」——
在這個叢集上不成立。所以理解層的價值不在呼叫 API，在
**把不可信的輸出變成可信的資料**：剝圍欄 → 程式驗 schema →
**證據查核（每個 `evidence` 必須真的出現在 OCR 出來的 text 裡）** → 不合就重問一次。

那個證據查核是免費的，而且是唯一擋得住幻覺的機制。

## 六、想 fork 之前先過這三題

1. 我 10 分鐘內跑得起來嗎？
2. 它省下的是**我不會寫**的東西，還是我 20 分鐘就能寫的東西？
3. 授權是 MIT 或 Apache 嗎？

三題有一題答不出來就別碰。

這次的答案是：核心不 fork，只偷兩樣 —— FilePilot AI 的 journal 格式（看 10 分鐘、抄 30 行），
以及之後如果要做桌面寵物，那個透明置頂視窗的 Electron 外殼確實值得 fork。

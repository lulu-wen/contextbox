# 視覺模型調查

調查於 2026-09-13。任務：**一張截圖 → 看懂 → 吐出結構化 JSON**，繁體中文，跑在自己的機器上。

星數與授權在 2026-09-13 用 GitHub API 驗證過。

---

## 先講實測結果（比任何 benchmark 都重要）

在自家內網閘道上，拿一張真的繁中公告截圖（900×560，台大助學金公告）測出來：

| 發現 | 內容 |
|---|---|
| **能看圖的只有一個** | `gemma-4-E4B-it`。另一個標示多模態的模型帶圖一律 HTTP 400 |
| **OCR 品質很好** | 每一行都讀對，包含 **民國 115 年 → 2026 的換算** |
| **結構化輸出全部無效** | `json_schema` strict／`json_object`／`guided_json` **三種都被忽略**，永遠包在 ` ```json ` 圍欄裡，而且會違反 enum |
| **會幻覺** | 同一張圖，短 prompt 時把「國立臺灣大學」讀成「國立嘉義大學」 |
| 速度 | 長 prompt 約 44 秒，短 prompt 約 5 秒 |

### 這三件事改變了設計

`SPEC-檔案與截圖.md` 第 7 節原本假設「帶 `guided_json`，vLLM 會強制格式」——
**在這個叢集上不成立。**

所以理解層的價值不在呼叫 API，在**把不可信的輸出變成可信的資料**：

```
剝 ```json 圍欄  →  程式驗 schema（enum、key 白名單）
                 →  證據查核（每個 evidence 必須真的出現在 text 裡）
                 →  驗不過就重問一次
```

**那個證據查核是免費的，而且是唯一擋得住幻覺的機制。**

## 通用視覺模型

| 模型 | 大小 | 授權 | 備註 |
|---|---|---|---|
| **[Qwen3-VL](https://github.com/QwenLM/Qwen3-VL)**　19936★ | 2B／4B／8B／32B ＋ MoE 30B-A3B／235B-A22B | **Apache-2.0** | **主線候選。** 8B 在小模型裡文件閱讀最強（DocVQA 96.1、MMMU 69.6），256K context，vLLM 0.11+ 原生支援 |
| **[Gemma 4](https://ai.google.dev/gemma/docs/core/model_card_4)（E4B）** | E4B（有效 4B） | Gemma 授權 | 明確支援螢幕與 UI 理解、文件解析、多語 OCR，128K context。**目前唯一實測可用的** |
| [GLM-V（4.5V／4.6V）](https://github.com/zai-org/GLM-V)　2385★ | — | **Apache-2.0** | 4.6V 支援 32 種語言 OCR，低光、模糊、傾斜都讀得到 |
| InternVL 系列 | — | 開源 | OCRBench 上輸給同級的 Qwen |

### 為什麼主線選 Qwen3-VL-8B

1. **Apache-2.0**，沒有限制
2. vLLM 原生支援 —— **`guided_json` 真的會被強制**，這正是現在缺的那一塊
3. 跟已經在跑的 Qwen 系列同家族，**manifest 照抄、踩過的坑一樣**
4. 8B 在 128GB 統一記憶體上綽綽有餘；品質不夠再上 32B（Q4 約 20GB）

## 為什麼現在**不**拆成兩段

技術上可以：OCR 專用模型抄字 → 文字模型做語意。更快、更準、更便宜。

**但 ContextBox 要的不只是文字**，還有分類、事件、待辦、缺件提醒、個人事實。
一次 VLM 呼叫就全拿到，跟 `SPEC-檔案與截圖.md` 第 7 節的設計一致，
而且少一個要維護的元件。

**等到速度或準度真的不夠，再拆。** 那時候 `config.model` 改一行就能換。
